# Frontend — Design & Architecture Guide

> Source of truth for this Next.js frontend. Read before adding pages, components, or data-fetching code.

## Tech Stack

| Area | Technology |
|---|---|
| Framework | Next.js (App Router) |
| Language | TypeScript (strict) |
| Styling | Tailwind CSS (+ shadcn/ui, if selected) |
| Data fetching | `@tanstack/react-query` v5 |
| HTTP client | `ofetch` (single shared instance in `lib/ofetch/http.ts`) |
| Auth | Better Auth (session cookie shared with the backend), if selected |

## Architectural Doctrine: Feature-First, Layered by Scope

- `app/` contains **routing primitives only** — pages, layouts, route handlers. No business logic, no direct HTTP calls.
- Domain logic lives in `features/<feature>/` capsules (created as modules are added, e.g. auth). Each feature owns its own components, queries, and types — features never reach into another feature's internals.
- Shared, non-domain-specific code lives in `components/` and `lib/`.

## Directory Structure

```
app/                     ← Routing primitives only (pages, layouts, route handlers)
  (public)/               ← Public marketing/auth pages
  layout.tsx              ← Root layout (global CSS, providers)
  globals.css

components/
  ui/                     ← shadcn/ui primitives only (button, dialog, table, …) — never feature-aware
  global/                 ← Cross-app reusable components (form fields, mode toggle, pagination)
  providers/              ← Client providers (QueryClient, theme, etc.)

features/                ← One capsule per domain feature (added by modules, e.g. `features/auth/`)
  <feature>/
    components/            ← Feature-specific UI
    queries/                ← TanStack Query hooks (`*.query.ts`, `*.mutations.ts`)
    types/                  ← Feature-specific types/schemas

lib/
  ofetch/http.ts           ← Single shared HTTP client instance — never call ofetch/fetch directly elsewhere
  env.ts                  ← Public env validation (`NEXT_PUBLIC_*`)
  utils.ts                ← `cn()` and small shared helpers
```

## Component Organization Rules

| Scope | Location | Allowed to depend on |
|---|---|---|
| UI primitives | `components/ui` | `lib/utils` only |
| Global reusable UI | `components/global` | `components/ui`, `lib/*` (never `features/*`) |
| Feature UI | `features/<feature>/components` | `components/ui`, `components/global`, `lib/*`, its own feature's queries/types |

## Framework Boundaries (Next.js)

| Concern | Environment | Location |
|---|---|---|
| Page layout, metadata | Server | `app/**/page.tsx` |
| Data mutation/query hooks | Client | `features/*/queries/*` (file must start with `"use client"` if it uses hooks) |
| HTTP transport | Either | `lib/ofetch/http.ts` — the only place that imports `ofetch` |

Rules:
- Any file using React hooks must start with `"use client"`.
- Every query param page (`searchParams`) must treat it as a `Promise` and `await` it before use.

## Data Fetching Conventions

- All HTTP calls go through the shared `api` instance in `lib/ofetch/http.ts`. Never instantiate a second HTTP client.
- Reads/writes are wrapped in TanStack Query hooks colocated with their feature (`features/<feature>/queries/<feature>.query.ts`, `*.mutations.ts`), not called ad-hoc inside components.
- Query keys are defined once per feature and exported for reuse — do not inline ad-hoc key arrays across multiple call sites.

## Conventions

- `components/ui` is regenerated by `shadcn` — do not hand-edit generated primitives beyond what the CLI produces.
- Keep `app/` pages thin: fetch/mutate through feature queries, render through feature/global components.
- Environment variables consumed on the client **must** be prefixed `NEXT_PUBLIC_` and validated in `lib/env.ts`.
